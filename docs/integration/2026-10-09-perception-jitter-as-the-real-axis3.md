# 感知抖动（Perception Jitter）是第③轴的真问题：从"传感器噪声"到"track 级时序不稳定"

> 日期：2026-10-09
> 触发：用户 realization——rino data 与 nuPlan 的理想输入差别不在"传感器噪声"，而在**线上感知模块的 track 级时序不稳定**（CIPV 等障碍物抖动 → 自车规划走形）。
> 关联：`docs/integration/2026-10-09-pufferdrive3-gap-analysis-for-own-data-lake.md`（本文锐化其 G7）。

---

## 1. 现象定义（精确化）

| | nuPlan 式理想输入 | rino data（线上感知） |
|---|---|---|
| 性质 | 近似**无噪声、时序一致**的 track | **track 级时序不稳定** |
| 表现 | 位置/速度/朝向平滑，ID 稳定 | 位置/速度/朝向**抖动**、间歇漏检、ID 跳变、时延 |
| 统计结构 | 近似 i.i.d. 小扰动 | **时间相关**（jitter 有记忆）、结构性、按目标角色异质 |
| 版本 | 固定 | **持续迭代，分布漂移** |

**关键区分**：这不是"传感器高斯噪声"问题，而是**感知/跟踪算法的时序不稳定性**问题。i.i.d. 噪声注入无法复现它的核心特征（自相关、突发漏检、ID 跳变）。

**最痛的点**：CIPV（Closest In-Path Vehicle，路径内最近车）的抖动直接激励纵向控制 → 规划轨迹震荡/走形。即噪声对**决策关键目标**的伤害是放大的，均匀注入是不够的。

---

## 2. 为什么这是本方案的"命门级"问题

1. **仿真 track 相对真实感知是"特权"的**。IDM/replay/self-play 生成的 agent 状态干净且时序一致。与 Pictura"特权向量 vs 相机"的论证**同构**，只是特权层级从"像素"下沉到了"track"：**干净仿真 track 之于真实感知 track，正如特权向量之于相机像素**。
2. **replay 与 self-play 的观测噪声天然不一致**：
   - replay + M1：Nova 看到**真实感知抖动**；
   - IDM/self-play：Nova 看到**干净仿真状态**。
   混合训练若不加噪声注入，等于让模型在**两种可观测性分布**间横跳——不解决问题，还制造不一致。
3. **16 帧历史是模型唯一的滤波器**。Nova 的 16 帧 agent 历史是学习"用时间维度平滑"的唯一接口；若历史也干净，模型**学不会**过滤抖动。
4. **感知持续迭代 → 训练数据永远落后部署**。目标是**对噪声分布域随机化**，而非匹配单版本；并建立**版本化监控**（数据噪声分布 vs 线上噪声分布）。
5. **它会污染归因**（回到最初的关切）：规划走形时，你无法区分"planner 能力问题"与"输入抖动问题"——除非训练/评测的噪声分布可控且已知。

---

## 3. Gap 重写：G7 = track 级噪声模型（而非 pose noise）

原 G7 只写了"pose/detection 噪声注入"。应重写为：

| 子项 | 内容 | 现状 |
|---|---|---|
| G7.1 噪声表征 | 从日志统计：CIPV/关键目标的 pos/vel/heading 抖动幅度 + **自相关函数**；漏检率与持续时长；ID 跳变率（交叉/遮挡）；感知时延分布；**按感知版本分组** | ❌ 无 |
| G7.2 时间相关噪声注入 | 用匹配自相关的随机过程（OU / 带记忆重采样）注入，**非每帧独立**；对 CIPV 加权 | ❌ 无（`8/9_bernhard_dev` 有 pose/brownian，但仍是简单噪声） |
| G7.3 历史级一致性 | 噪声必须进入 16 帧历史，而非仅当前帧 | ❌ 无 |
| G7.4 版本域随机化 | 多版本噪声分布间随机化 + 线上分布漂移监控 | ❌ 无 |
| G7.5 抖动专用评测轴 | CIPV 抖动下的规划平滑性（jerk、轨迹振荡、TTC 波动、加速度振荡频率），独立于 collision/goal | ❌ 无 |

## 4. 一个必须先拍板的架构问题：抖动鲁棒性住在哪一层？

| 方案 | 做法 | 代价 |
|---|---|---|
| **(a) 上游感知/跟踪平滑** | 在进入 planner 前滤波 | 可能引入额外时延；且你未必能改线上模块 |
| **(b) planner 自己学过滤** | 靠 Nova 的 16 帧历史在策略里隐式滤波 | 需要训练数据历史带真实抖动；可能与上游平滑叠加而过度保守 |
| **(c) 独立状态估计层** | 介于两者之间 | 新增组件与接口 |

**对训练数据的要求完全不同**：
- 选 (b) → "历史里带真实抖动"是**硬需求**；仿真 self-play/IDM 模式必须注入匹配噪声。
- 选 (a) → 训练可以更干净，但部署时 planner 面对的是"平滑后分布"，需要另配训练/评测。
- 选 (c) → 需先定义估计层的输出契约，再决定 planner 观测。

## 5. 建议的下一步（低成本、高信息）

1. **从一份 rino 日志中抽 CIPV 抖动统计**（对平滑参考或真值算残差 + 自相关 + 漏检/ID 跳变），产出一张"噪声参数表"。
2. 用这张表在 PufferDrive 里实现**时间相关噪声注入**（G7.2+G7.3），先在公开 WOMD 场景验证"注入后规划抖动可复现"。
3. 加一条**抖动评测轴**（G7.5），并在纯 self-play / 混合对手两种训练下对比。
4. 依据结果决定 §4 的架构归属。

---

## 6. 一句话

> 你方案里第③轴真正的敌人不是"传感器噪声"，而是**线上感知的 track 级时序不稳定（CIPV 抖动）**；干净仿真 track 是"特权观测"，必须在训练/评测里用**时间相关、版本化、按目标加权**的噪声把它补齐——否则 planner 学到的是"干净世界里的最优"，一上真车就被 CIPV 抖动带偏，且你无法归因。
