## 0. 一句话

这次会话**没有写训练代码**。它做的是把三个模糊主张——"地图能搬进来"、"RL 能出海量"、"bad case 能修"——逐个拆成**可测的量**，再把它们接到一条**可复现的执行链**上。

> [!IMPORTANT] 结论先行
> 地图能不能搬、RL 能多快、约束够不够，这三个问题的答案都不在文档里，而在**三个实测数字**里：感知 70 m、数据年龄 0.53 s、积分器偏差 3e-5 m。先有尺子，再谈模型。

---

## 1. 起点：三个问题，一个真实决策

| 层 | 内容 |
|---|---|
| **表面问题** | PufferDrive 的能力边界？能不能吃 Apollo HD map 格式？能不能用 bag（occ polygons + BEVDet bboxes）做海量 RL，训出 robust planner？ |
| **真实决策** | 要不要把"自有地图/日志 → 场景"这条 ETL 排到最前面？还是先承认 PufferDrive 的价值在**世界与反馈回路**，几何多样性用现成数据？ |
| **隐含成功标准** | 不是在仿真里刷分，而是**部署模态下**、在**没见过的地图与感知抖动**下都不退化，并且**能持续吃 bad case**。 |
| **硬约束** | 5000+ 车数据只采一次；12 个月；部署契约是 Nova；计算资源有限。 |

## 2. 五个转折（触发 → 证据 → 裁决 → 产物）

<!-- step:1 事实层：先把"能做什么"钉死 -->
**触发**：需要知道 PufferDrive 到底能吃什么。

**证据**（读代码，不是猜）：

- 观测是**纯向量化**：ego + 16 partner + 70 lane + 50 boundary + 4 traffic control（`drive.py:263-275`）
- 地图 `.bin` 其实是 **scene bundle**：agents 全轨迹 + roads + traffic + `scenario_id`（`map_data.h:325-720`）
- objects 段被 **`fseek` 直接跳过**（`map_data.h:636-646`）→ occ polygon 目前**无处安放**
- 仓库里**没有任何 map loader**：nuPlan/WOMD 的 bin 全部来自外部转换器（py123d / ScenarioMax）
- Apollo 地图实测：**21,174 个 tile / 148 GB / 31 站点**，protobuf + UTM

**裁决**：地图不是"搬进来"，而是**分成两个消费者**。
<!-- /step -->

<!-- step:2 分歧：地图进 Core 还是进编码器 -->
**触发**："没有 Apollo HD map，地图作为 env 一部分进 encoder 的需求就无法满足。"

**证据**：Core 的 `RoadMapElement` 只有 `type / entry / exit / speed_limit`；而编码器要的是 `lane_turn_type / boundary_type / overlap 拓扑`。

**裁决**：**一源两投影**——仿真视图（几何/连通/交通控制）给 Core，编码视图（Apollo 原生语义）给编码器。反推会丢信息。

**产物**：`docs/adr/0007`、`docs/vehicle_profile.md`
<!-- /step -->

<!-- step:3 关键变量：部署到底吃什么 -->
**触发**：所有设计都取决于一件事——线上 planner 的输入契约。

**证据**：owner 回答 **A：Nova，特权向量**（HD map + 16 帧 track + occ + TL）。

**裁决**：接 A ≠ 把 Nova 当契约。owner 随后明确"**不必拘泥 nova**，能拿到 SOTA 就行"。
→ **canonical spec 模型无关；Nova 降级为基线 + 参考实现。**

**产物**：`docs/adr/0007` D2
<!-- /step -->

<!-- step:4 方法论：RL 是核心，bad case 是种子 -->
**触发**：owner 指出 RL 才是核心手段，并用 Terra 系列举证。

**证据**：TerraZero 纯 self-play、零人类演示，拿到 nuPlan val14 **94.19（#1）**、InterPlan **70.87（#1）**；吞吐 560K–2.8M agent-steps/s。

**裁决**：RL 承担 0→1；**bad case 承担 1→100**，且它是**场景种子 + 约束束**，不是标签。
反馈契约 = **A-only**：只有约束、没有专家修正、没有好样本。
分布口径：违规型 **80%** / 体感型 **20%**。

**产物**：`docs/2026-11-04-badcase-as-scenario-seed-constraint-loop.md`（1→100 回路、20 条约束模板、两个 KPI）
<!-- /step -->

<!-- step:5 落地：从"能跑"到"能验" -->
**触发**：执行层的三个小问题——动作、积分器、限幅。

**证据**：

- Nova 的轨迹自带控制量 `(acc, κ)`；`a_lat = κ·v²` 与仿真可逆对接
- 但 PufferDrive 的 jerk 接口有三处会**静默改写**控制量：反解饱和、`c_throttle/c_steer` 缩放、零穿越吸附
- Nova 的积分器是**半隐式 Euler**，PufferDrive 是**梯形 + 精确圆弧**
- 实车参数：δ_max 0.6056 rad、δ̇_max 0.4234 rad/s → **满舵要 1.43 s**（仿真只给 0.92–1.11 s）

**裁决**：先造尺子——`ACTION_TYPE_CONTROL` + `model_euler` + `skip_actuator_limits`，然后**数值对拍**。

**产物**：4 个 C 测试 + 7 个对拍测试；积分器偏差 **1.7e-5–3.4e-5 m / 6 s**
<!-- /step -->

## 4. 三条因果链

### 4.1 执行链：动作语义 → 积分器 → 对拍

```
模型输出 (acc, κ)
   │
   ├─ 仿真若走 jerk 接口 → 被三处静默改写（反解饱和 / 奖励系数 / 零穿越吸附）
   │     └─▶ 无法归因：车没按模型走，是谁的错？
   │
   ├─ 新增 ACTION_TYPE_CONTROL → 直连 (a_long, κ)
   │     └─▶ 还剩一个问题：积分器不一样（梯形+圆弧 vs 半隐式 Euler）
   │
   ├─ 新增 integration_scheme=model_euler
   │     └─▶ 对拍通过：60 步偏差 3e-5 m（float32 噪声）
   │
   └─ 对拍时发现：Nova inference 会对前 4 个加速度做 wash-in
         └─▶ 不洗：6 s 偏 0.39–0.92 m（比积分器误差大 4 个数量级）
               └─▶ 裁决：wash-in 归桥接层，已有测试双向钉住
```

### 4.2 世界链：地图 → 双视图 → occ → 两个域

```
Apollo HD map (protobuf, 21k tiles)
   │
   ├─ 仿真视图：几何 + 连通 + 交通控制 ──▶ PufferDrive bin
   │     └─ 只服务物理/碰撞/route/IDM
   │
   ├─ 编码视图：Apollo 原生语义 ────────▶ encoder
   │     └─ 不经过 Core（否则丢 boundary_type / turn_type / overlap）
   │
   ├─ occ：当前 loader 直接跳过 objects，且 object 只有 9 条 float 轨迹
   │     └─▶ 裁决：occ 是物理实体 → 必须新增表示（碰撞 + 导出）
   │
   └─ 场景来源：走廊锚定（有日志可对拍） + 全图漫游（无真值，靠内禀约束）
         └─▶ 两个合法性域，两套裁判
```

### 4.3 迭代链：bad case → 种子 → 约束 → 回归

```
bad case（bag + t + 可下载 HD map）
   │
   ├─ 只有"约束"，没有专家修正/好样本/标签（A-only）
   │
   ├─ 违规型 80%：18 项 metrics 就是谓词 → 全自动挖掘，零标注
   │     └─ 入口需物理可行性门禁（实测有 38 m/s 的定位跳变）
   │
   ├─ 体感型 20%：必须人工翻译成量化谓词
   │     └─ 翻译不了的就明确放弃（"约束全绿、司机不认"是这个方案最可能的失败形态）
   │
   └─ 回路：场景切片 → 场景族 → 可行性裁判 → RL fine-tune → 回归保留
         └─ KPI 不是分数，是「约束覆盖率」与「回归保留率」
```

## 5. 本次测出的关键数字

| 量 | 值 | 它改变了什么 |
|---|---|---|
| 前轮最大转角 / 角速率 | 0.60564 rad / 0.42336 rad/s | 仿真限幅从 0.667/0.6 改到真值 |
| 直线 → 满舵 | 1.43 s（仿真原 0.92–1.11 s） | 模型学的"可行性边界"原来偏乐观 35–55% |
| 运营速度 | 12.5 m/s（AD 能力，非底盘硬限） | 不能写成动力学夹，要写成约束 |
| 底盘设计速度 | 50–60 km/h | 动力学夹应落在这里 |
| a_lat 实测代理 | 8.0 m/s²（596 s 样本，未冻结） | 替换那个把高速转弯砍半的 ±4 |
| 感知最远距离 | ≈70 m（>100 m 为 0） | 仿真 partner 观测 200 m → 差 2.8 倍 |
| 控制侧数据年龄 | 0.53 s（12.5 m/s 下盲开 6.6 m） | 仿真零延迟 → 策略比实车激进 |
| 积分器偏差 | 3e-5 m / 6 s | 执行链干净 |
| 不做 wash-in 的偏差 | 0.39–0.92 m / 6 s | 桥接层必需预处理 |
| 数据质量 | 38 m/s、κ>κ_max 的帧存在 | 场景抽取必须门禁 |

## 6. 现在的位置

| 能做 | 不能做（以及为什么） |
|---|---|
| 直连执行 `(acc, κ)` 并用 `model_euler` 精确复现模型轨迹 | 不能把 `(acc, κ)` 原样喂进去——wash-in 还没进桥接层 |
| 用 `metrics_array` 18 项自动挖违规帧 | 不能扫 rino bag——bag→scene 转换器还不存在 |
| 量任意 Apollo bag 的感知距离/延迟/横向包络 | 不能训练——canonical spec 未冻结，且 `pufferlib._C` 缺 C++20 |
| 跑 C 单测（10 个程序）与对拍（7 例） | 不能证明"仿真里变好 = 实车变好"——回归相关性那层还没建 |

## 8. 一句话总结

**这次会话的产出不是"能跑的模型"，而是一把尺子和一张地图**：尺子能量出仿真与实车在动作、积分、观测、延迟上的偏差；地图标出了从 bad case 到回归集的回路。**下一步不是继续造尺子，是冻结 canonical spec——它是唯一挡在所有实现前面的东西。**
