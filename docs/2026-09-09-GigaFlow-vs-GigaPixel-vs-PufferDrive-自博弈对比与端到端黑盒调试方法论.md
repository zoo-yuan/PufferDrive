## 0. TL;DR

| | **GigaFlow** | **PufferDrive** | **GigaPixel** |
|---|---|---|---|
| 一句话 | 向量化 BEV 自博弈的"规模极限"，证明**纯自博弈**可产出鲁棒拟人驾驶 | 向量化 BEV 自博弈的"工程极限"，把端到端 RL 训练吞吐推到单 GPU 32 万步/秒 | 把自博弈从 BEV 向量观测**推进到像素级端到端**的首次成功尝试 |
| 观测 | 向量化（地图+智能体） | 向量化 ego-centric（1848 维） | 透视渲染 **pixels**（简化 bbox 世界） |
| 关键方法 | 大规模并行自博弈 RL | PPO + 对称多智能体自博弈 + PufferLib 向量化 | **Self-Play DAgger**：特权 RL teacher 在线蒸馏 pixel student |
| 吞吐 | 8-GPU 节点 42 年驾驶经验/小时 | 单 GPU ~320,000 agent-steps/s | ~50,000 agent-steps/s |
| sim2real | 真实记录场景闭环测试 | human-replay / WOSAC 评估 | 轻量**感知适配**到真实传感器数据 |
| 与你关心的迭代 | 证明"规模→鲁棒" | 证明"速度→实验循环快→算法进步快" | 首次打通"像素 e2e + 自博弈 + 归因断层(teacher/student)" |

**核心判断**：三份工作是同一条思想主线（*数据驱动的多智能体仿真 + 大规模自博弈训练端到端策略*）在三个不同"战场"的攻坚——**GigaFlow 攻规模、PufferDrive 攻速度、GigaPixel 攻观测模态（BEV→像素）**。它们共同构成理解"端到端 model planner 如何快速进化、出了问题如何定位归因"的最佳实验场。

## 1. 三份工作档案

### 1.1 GigaFlow（2025-02，arXiv 2502.03349）
- **主张**：*Robust Autonomy Emerges from Self-Play*——鲁棒且拟人的驾驶行为可以完全从自博弈中涌现，**无需任何人类驾驶数据**。
- **规模**：累计 16 亿公里仿真驾驶；单 8-GPU 节点每小时合成 42 年"主观驾驶经验"（并行 agent 数 × 时长）。
- **结果**：在三个独立自动驾驶基准上达到 SOTA；在**真实记录的驾驶场景中与人类车流混合闭环测试**中超过此前 SOTA；仿真中平均 **17.5 年连续驾驶才发生一次事故**（鲁棒性代理指标）。
- **方法画像（据摘要与同源博客）**：bached 仿真器、向量化观测、多智能体同策略自博弈；奖励 = 到目标/不碰撞/不出路为主；纯 PPO 式 on-policy RL 从零开始。
- **血缘**：作者含 Eugene Vinitsky（Nocturne/GPUDrive 一作/Emerge Lab）与多位工业级仿真 RL 资深作者（Petrenko、Wijmans、Krähenbühl、Koltun 等）。

### 1.2 PufferDrive（2025 v2.0，本仓库）
- **主张**：让 RL 自动驾驶的**经验生成速度**不再成为瓶颈——"仿真速度直接决定 RL 能多可靠地解决现实问题"。
- **吞吐**：单 GPU 端到端训练 ~320,000 steps/s（Nocturne 的 160 倍、GPUDrive 的 ~6 倍）；1 万张 Waymo 多智能体场景 15 分钟达到此前 GPUDrive 24 小时才达到的成绩。
- **能力**：PPO + 共享策略对称自博弈、mixed-play（可调自博弈/日志回放比例）、长时程 CARLA 多目标驾驶、WOSAC 分布真实性评估、human-replay 兼容性评估、浏览器共驾 demo。
- **定位**：不是一份"训练出某辆车"的论文，而是一个**开源基础设施**——把 Nocturne→Gigaflow 的"自博弈能行"压缩成"谁都能 15 分钟复现"。
- **血缘**：Nocturne(2022) → GPUDrive(2024) → PufferDrive；与 GigaFlow 同年并行。

### 1.3 GigaPixel（2026-06，arXiv 2606.19641）
- **主张**：此前自博弈方法都假设 **BEV 向量观测**，与"直接从传感器(像素)工作"的端到端策略不兼容。GigaPixel 首次让**像素级端到端**驾驶模型能享受自博弈的规模红利。
- **方法**：
  1. **Gigapixel 仿真器**：透视渲染 + 简化的 bounding-box 世界（不做昂贵的照片级真实渲染），~50K agent-steps/s；
  2. **Self-Play DAgger**：纯像素直接 RL 在端到端模型尺度下样本效率过低 → 让**特权 RL teacher**（看到真值/向量世界）在自博弈中产生 on-policy 数据，pixel student 在线蒸馏；
  3. **轻量感知适配**：把自博弈学到的策略适配到真实传感器数据，桥接 sim-to-real。
- **结果**：在 **HUGSIM 与 NAVSIM-v2** 上无人类轨迹监督即达竞争力水平；**规模增加带来近似线性性能增益**——自博弈成为训练端到端模型的"可扩展"策略。
- **血缘**：Rowe/Girgis/Pal/Paull（Mila）+ **Daphne Cornelisse、Eugene Vinitsky（Emerge Lab，与 PufferDrive 同一实验室）**。

> **勘误**：PufferDrive 官方博客 `pufferdrive-2.0.md` 中 GigaFlow 的 arXiv 链接写作 `2501.00678`（实为物理论文），正确编号是 **arXiv:2502.03349**。

## 2. 历史脉络：一条主线，三场攻坚战

### 2.1 时间线

```
2022  Nocturne：数据驱动(world-on-rails)仿真，证明"多智能体自博弈 RL 能学开车"
      —— 2,000 SPS，80% 目标达成需 ~2 天；瓶颈=经验成本
2024  GPUDrive (Madrona)：GPU 批量仿真到 100 万 FPS 级
      —— ~50K 端到端训练 SPS，~1.7 小时到 80%
      ├─▶ 并行侧 GigaFlow (2025.02)：向量化自博弈 × 极致规模
      │    → 证明"规模足够大时，鲁棒性/拟人性涌现"；16 亿 km、17.5 年/事故
      └─▶ PufferDrive (2025)：PufferLib 重写，单 GPU 320K SPS
           → 证明"速度提升 = 实验循环加速 = 研究/调试生产力提升"
                 │
                 ▼ (同一批人：Cornelisse / Vinitsky)
2026  GigaPixel：自博弈 从 BEV向量 走向 像素端到端
      → 补上"自博弈只能喂给向量 planner"的短板，打通 sensor→plan
```

### 2.2 三条线的继承关系

- **Nocturne→GPUDrive→PufferDrive→GigaPixel 是"直系血亲"**：共享同源地图数据（WOMD）、共享"从场景初始条件出发做多智能体自博弈"的实验协议、共享评估思想（human-replay、goal/collision 度量），人员高度重叠（Vinitsky、Cornelisse）。
- **GigaFlow 是"同思路的独立验证"**：工业团队用向量化观测把自博弈规模推到当时最大，且**宣称完全不用人类演示数据**——它和 PufferDrive 互为"算法主张 vs 工程普惠"的两面。
- **GigaPixel 站在整条脉络的肩膀上**：它继承了"自博弈可扩展"的信念（来自 GigaFlow 的规模证据与 PufferDrive/GPUDrive 的工程经验），把缺失的最后一块拼图——**像素观测**——补上，同时引入了 teacher/student 架构（这也是后续归因方法论的天然接口，见第 6 节）。

## 3. 三者的异同

### 3.1 共同点（"是什么让它们属于同一个家族"）

1. **自博弈是核心训练引擎**：所有被控 agent 共享一份策略，互为对手/同伴；不依赖（或仅极轻量依赖）人类专家轨迹作为监督。
2. **数据驱动仿真（grounded simulation）**：地图/初始布局来自真实数据（WOMD/CARLA），保证博弈起点在真实分布上，防止学到完全脱离物理合理域的行为。
3. **奖励结构高度一致**：到目标(+) 与 碰撞/出路(-) 构成的稀疏目标函数 + 平滑类惩罚；不把"拟人"写进奖励，期望它**涌现**。
4. **"规模即算法"信念**：RL 在十亿样本量级才可靠 → 瓶颈是仿真吞吐 → 三份工作都以吞吐为第一工程目标（42 年/小时、320K SPS、50K SPS）。
5. **评估都包含"与人类/真实世界对齐"的闭环手段**：GigaFlow 用真实记录场景混合测试；PufferDrive 用 human-replay + WOSAC；GigaPixel 用 HUGSIM/NAVSIM-v2 + 感知适配。

### 3.2 差异表

| 维度 | GigaFlow | PufferDrive | GigaPixel |
|---|---|---|---|
| 观测模态 | 向量化（BEV/图） | 向量化 ego-centric | **透视像素**（简化为 bbox 世界） |
| 策略输入 | planner-level | planner-level | **传感器级（端到端）** |
| 仿真渲染 | 无渲染/矢量 | 矢量 + 可选 Raylib 可视化 | 透视渲染（含遮挡/视角线索） |
| 训练算法 | 大规模自博弈 RL | PPO + 共享策略对称博弈 | 自博弈 DAgger（特权 teacher → pixel student） |
| 硬件/速度 | 8-GPU 节点、40+ 年经验/时 | 单 GPU ~320K SPS | ~50K SPS |
| 主要 benchmark | 3 套独立闭环基准 | WOMD 子集 + human-replay + WOSAC | HUGSIM、NAVSIM-v2 |
| 人类数据使用 | 训练 0 使用；测试在真实场景 | 训练 0 使用（WOMD 提供地图/起点/目标，不提供行为监督）；Carla 同理 | 无轨迹监督；真实传感器数据仅用于**感知适配** |
| 开源/可复现 | 未开源（工业侧） | **全开源 + 15 分钟复现** | 研究侧，仿真器+方法公开 |
| 典型失败模式覆盖 | 长尾交互鲁棒性 | 算法迭代/基准实验效率 | 像素 e2e 的 sim-to-real |
| sim2real 策略 | 真实场景闭环测试 | 不承诺落地；提供评估手段 | 显式"感知适配"两步法 |

### 3.3 三个关键深水区差异（决定未来走向）

**(a) 观测模态是分水岭：向量 vs 像素**
- 向量观测把"感知"这个难题外包给了数据预处理——策略吃到的已经是上帝视角真值，所以 GigaFlow/PufferDrive 学到的本质是**"世界已知时的驾驶行为（决策/规划）"**。
- GigaPixel 首次在闭环自博弈中引入**透视渲染**，让策略必须自己从像素里"看出"遮挡、远近、视角畸变——但代价是吞吐掉了一个量级（320K→50K），且渲染保真度远低于真实世界，于是必须靠"感知适配"补 sim-to-real。

**(b) 训练范式：单阶段 RL vs teacher/student 蒸馏**
- GigaFlow/PufferDrive：直接 RL 更新唯一网络。
- GigaPixel：因为"像素级直接 RL 样本效率太低"，退回 **privileged learning 范式**（teacher 吃真值向量世界、跑得快、教得好；student 吃像素、被蒸馏）。这实际上是把经典"privileged imitation / student-teacher"（如 affordance learning、安全强化里的专家蒸馏）与 on-policy 自博弈数据流结合。

**(c) 速度 × 保真 × 规模的不可能三角**
- PufferDrive 选了速度（最大实验循环数）；GigaFlow 选了规模（同一套向量世界堆算力）；GigaPixel 选了保真（渲染）但牺牲了速度。三者都还没有同时拿到"照片级渲染 + 30 万 SPS + 像素级 e2e"——这就是下面要说的潜力空间。

## 4. 能力边界（各自的"不能"）

### 4.1 GigaFlow 的边界
- **感知盲区**：BEV 向量观测意味着策略**不面对真实传感器挑战**（遮挡、天气、噪声、标定误差、检测漏检）。它证明的是"planner 本身可以很鲁棒"，而不是"完整的自动驾驶栈很鲁棒"。
- **真实落地证据**：摘要中的"真实场景中与人车流混合测试"是**在仿真回放环境里闭环**，未披露大规模真实道路车队验证；sim-to-real 残留风险未直接回答。
- **复现性**：未开源，42 年/小时与 16 亿 km 的规模对普通团队不可企及；其"鲁棒性=事故间隔"是仿真内指标，不是可证安全。
- **人类行为多样性**：纯自博弈对手都是"自己"，如果目标奖励/地图分布有偏，学到的是"自家均衡"而非"人类均衡"（PufferDrive 用 human-replay/mixed-play 主动规避这一点）。

### 4.2 PufferDrive 的边界
- **同样吃向量观测**：它是"自博弈 RL 的快速实验台"，不是可上车的感知-规划栈；观测里连红绿灯都不支持（roadmap 承认），地图是 2.5D 无立交。
- **行为拟真上限**：`score`、`collision_rate` 是自博弈内部指标；human-replay eval 的"人类伙伴"是**固定日志**（README 自述"not a perfect eval"）；WOSAC 评估分布接近性但不等于真实世界安全。
- **单策略同质化风险**：默认所有 agent 共享策略 → 场景内可能出现"全体同一驾驶风格"的同质车流，缺少慢车/激进车/行人多样性（roadmap 也把 agent diversity 列为 3.0 方向）。
- **工程覆盖而非算法创新**：PPO + 稀疏奖励本身没有新算法；极端吞吐依赖 C 内核 + PufferLib 的深度优化，改动需重编译 C，算法侧定制成本高。

### 4.3 GigaPixel 的边界
- **吞吐-保真两难**：50K SPS（简化 bbox 渲染）仍比 PufferDrive 慢 6 倍；要提高渲染真实度（纹理/光照/传感器噪声）吞吐会进一步下跌，而真实度又正是像素 e2e sim-to-real 的关键。
- **teacher/student 断层**：teacher 吃真值世界训练出的行为，student 从像素学——当**感知出错**时 student 没有闭环反馈去修复感知（蒸馏只能教"在感知正确时该怎么做"）；感知适配用的是**真实离线数据**，仍可能存在闭环下未见过的感知故障。
- **benchmark 覆盖面**：HUGSIM/NAVSIM-v2 是仿真/重放闭环，不等于真实道路；"无人类轨迹监督"但**用了真实传感器数据做适配**——所以不是"完全不用人类数据"。
- **像素 RL 的样本效率天花板**：自博弈 DAgger 仍需 teacher 的 on-policy 数据量大、单步贵；端到端模型尺度上的探索仍是开放的效率难题。

## 5. 建议的潜力方向（三线交汇处）

1. **在向量速度上做像素训练**：把"透视渲染"做成 GPU 上的可批量化算子（PufferDrive 的吞吐哲学 + GigaPixel 的像素目标），目标是像素级 e2e 自博弈到 10 万+ SPS；这是把"不可能三角"推向"渲染廉价化"的工程方向。
2. **自适应传感器损伤训练**：在像素仿真里显式注入感知噪声（遮挡、退化、对抗 patch），让 student 在闭环中学会"感知不确定时如何开车"——直接补 GigaPixel teacher/student 断层。
3. **人群/联盟式自博弈（League Play + Policy Pool）**：GigaFlow/PufferDrive 的同策略博弈容易收敛到单一均衡。用**历史 checkpoint 池 + 异质策略（激进/保守/不同目标权重）**当对手，兼顾"难度课程"与"多样性"，也能防遗忘（见 6.5）。
4. **混合车流做拟真度锚**：PufferDrive 的 mixed-play 把"自博弈与日志回放"做成连续可调；把它推广为训练期全程的对手采样分布，可缓解纯自博弈的人类偏移，同时保留交互性——这是 GigaFlow 声称"涌现拟人"与 human-replay 折中的关键旋钮。
5. **把"鲁棒性指标"做成可优化目标**：GigaFlow 的"17.5 年/事故"只在 eval 期统计；未来可在训练目标里加入**碰撞责任分解、风险度量、可行驶区域合法性约束**，把鲁棒性从"事后统计"变成"在线可微反馈"。
6. **自博弈与数据闭环打通**：用自博弈仿真自动挖掘失败场景（碰撞/近失/加塞被逼停）→ 注入场景库 → 作为回归集（第 6 节的核心资产），反向指导真实路测数据采集——仿真不再只是训练器，而是**场景矿机 + 回归保险**。
7. **标准化跨模态基准**：三份工作各有私有的"自博弈分数"。建议社区统一一个"向量-像素-真车"三级可对拍的评估协议（如：同一场景集上，PufferDrive 向量策略 ↔ GigaPixel 像素策略 ↔ 路测），让模态与方法的贡献可分离测量。

## 6. 深度专题：端到端 model planner 的黑盒问题定位、归因与"不复发"快速迭代

> 你关心的核心痛点：端到端（尤其一段式）引入了黑盒——问题发生时不知道坏在哪一层；想快修又怕旧问题复发。三份工作恰好提供了完整的**调试基础设施思想**：**可闭环 = 可归因，可廉价重放 = 可回归**。

### 6.1 先定义两类架构的"黑盒形状"

**（A）两端式（两段式）端到端 model planner**
- 典型：感知（检测/占用/地图/预测，可能是子网络栈）→ planner（学习到的轨迹/决策头），整体联合训练（如 UniAD/VAD 类、稀疏/稠密范式）。
- 黑盒形状：**中间有一道可观测的"语义接口"**（目标框、轨迹、占用栅格）。问题可以粗定位到"上游喂错了 vs 下游决策差"，因为你能读出中间产物。
- 优点：中间任务可加监督/可监控 → 归因粒度较好。缺点：接口特征经过网络学出来，不一定忠实；错误会在接口处**累积放大**（感知小错 → 预测大错 → 轨迹离谱）。

**（B）一段式端到端**
- 典型：sensor（多相机/LiDAR）→ 轨迹/控制直接输出；决策不显式出现在任何中间量（如 Waymo E2E、diffusion planner 类）。
- 黑盒形状：**中间无人类可读语义**，只有隐空间表征。问题只能从"输入-输出对"层面观察。
- 优点：无累积误差、全局最优耦合。缺点：归因几乎只能靠**干预实验**（改输入/换背景/注入真值），没有天然的"审计截面"。

> 结论先行：**一段式比两端式更需要"外部归因实验室"**；而三份工作共同证明，**高速可闭环仿真就是那个外部实验室**——因为它能提供两样两端式都缺的东西：**真值 oracle（特权信息）**与**反事实场景编辑**。

### 6.2 黑盒问题的定位与归因：四步归因协议

无论一段式还是两端式，推荐把问题先跑过下面漏斗：

```
【现象】路测/仿真里出现某类失败（追尾、加塞被顶、压线、急刹幽灵、对行人无反应…）
   │
   ▼ Step 1 复现与最小化
   把现象沉淀为"最小可复现场景"（地图裁剪 + 若干背景车 + 固定时间戳）
   → PufferDrive/场景编辑器在此的价值：WOMD/CARLA 场景可编辑、可精确重放
   │
   ▼ Step 2 分层归因（核心）
   同一场景上跑一组"干预对照"，把失败归到具体模块/模态/分布：
   ┌─ 感知层归因：把 planner 输入替换为 oracle（真值检测/地图）再跑
   │    · oracle 输入下通过 → 感知问题（漏检/误检/测距/时序错位）
   │    · oracle 输入下仍失败 → 往下走
   ├─ 预测层归因（两端式）：喂真值历史轨迹 vs 模型预测轨迹
   │    · 预测错 → 交互预测问题；预测对仍失败 → planner
   ├─ 策略/规划归因：固定输入，把 planner 输出替换成"参考专家/规则轨迹"
   │    · 仍撞 → 环境动力学/奖励建模 bug（仿真错误！）
   │    · 不撞 → planner 决策分布问题
   └─ 分布归因：把失败场景插回训练集统计——
        · 场景在训练分布外(OOD)？→ 数据覆盖问题
        · 分布内但策略仍错？→ 奖励/优化问题（欠拟合、reward hacking）
   │
   ▼ Step 3 归因确认
   用反事实编辑验证：去掉/移动罪魁车辆、改变其意图轨迹
   → 失败消失 ⇒ 归因成立；不消失 ⇒ 还有第二原因
   │
   ▼ Step 4 打标签入库 → 转第 6.4 节修复
```

**对应到三份工作的语言：**
- "oracle 输入对照" = GigaPixel 的 **privileged teacher**（吃真值世界）与 PufferDrive 的 human-replay/`control_sdc_only`（只控自车、其余真值回放）——**架构上的 teacher/student 分层同时就是归因的审计接口**。
- "参考轨迹对照" = NAVSIM/WOSAC 的 **PDMS 类度量**（计划轨迹 vs 参考/真值轨迹的偏差）——把黑盒输出投影到可度量空间。
- "OOD vs 分布内" = 仿真吞吐给了你**大批量低成本统计**：PufferDrive 一小时可把同样 1000 个场景跑上千个随机种子，把"偶发失败"与"系统性失败"分开。

**一段式专属补充手段**（没有中间接口时的归因）：
1. **模态遮挡/抹除**：单相机遮挡、目标局部涂改、加 sensor dropout → 观察失败依赖哪个输入。
2. **中间表征探针**：加轻量 probe head（占用/速度/意图）在推理时旁路读出隐空间含义，找"表征里到底有没有那个关键信息"。
3. **行为层面归因**：不追内部，只按"行为签名"分类——急刹、轨迹曲率异常、反应时延超常 → 每个签名映射到常见根因族（感知时延、预测摇摆、规划视距短、奖励不齐）。
4. **teacher/student 联合评估**：同一个 planner 分别接 oracle 输入（privileged 模式）与真实感知输入跑闭环。两者差距即**感知引起的失败比例**（可直接引用 GigaPixel 架构做归因实验台）。

### 6.3 常见失败根因族与典型修复手段（映射表）

| 根因族 | 现象签名 | 归因实验 | 典型修复 | 复发风险 |
|---|---|---|---|---|
| 感知漏检/误检 | 对静止车/异形车无反应 | oracle 输入通过 | 补数据/修模型/加融合 | 高：需回归集 |
| 感知时延/错位 | 幽灵急刹、轨迹滞后 | 延迟注入对照 | 时序对齐、预测补偿 | 中 |
| 交互预测不足 | 加塞被顶、不让行 | 喂真值预测轨迹通过 | 加交互数据/自博弈 | 中 |
| planner 视距短/短视 | 高速弯道压线、late cut-in | 参考轨迹通过 | 加长程目标/改奖励 horizon | 中 |
| 奖励错配/reward hacking | 蹭目标点、钻空子绕路 | 看 reward 曲线与行为分离 | 改奖励结构（如 goal_speed 约束） | **高：极易复发** |
| OOD 场景覆盖不足 | 长尾(路口无灯/异形路口) | 训练分布统计 | 场景挖掘+自博弈补充 | 低(补库即可) |
| 策略退化/遗忘 | 修 A 后 B 复发 | 回归集全量跑 | policy pool/混合重放（见 6.5） | **高：系统性** |
| 仿真-真实 gap | 仿真好、路测差 | sim vs real 同场景对照 | 域随机化/感知适配/提高渲染 | 中 |

> 注意表里标"高复发风险"的行：**感知类**问题修的是"特定模式"，但模型是全局参数——修新样本必然扰动旧样本；**奖励类**问题最狡猾，因为它优化的是代理目标，任何补丁都可能被新的钻空子方式绕过。这两类必须依赖第 6.4/6.5 节的**回归门禁**。

### 6.4 快速稳妥修复：三层防线防"旧问题复发"

**第一层：把每个修过的 bug 变成"场景回归测试"。**
- 场景库（Scenario Bank）= 全项目最重要的调试资产。每个 bug → 一个带标签的最小场景文件（复用 PufferDrive 的二进制场景 + 场景编辑器格式），天然可版本化、可被 CI 跑。
- 每一次策略/数据/奖励改动后，全量回放场景库：
  - 旧 bug 场景：必须通过（**不复发门**）；
  - 新修复场景：必须通过（**修复生效门**）；
  - 抽取的随机/自博弈场景：作为对照（防过拟合到场景库本身）。
- 把"17.5 年/事故""sp_score""collision_rate""WOSAC realism"做成**自动门禁指标**，任何 merge 前必须不掉点。

**第二层：训练期防遗忘——把回归集"掺回"训练。**
- 只做 eval 时回放不够，还要让模型"忘不掉"旧技能：在训练 batch 中**持续混合重放**场景库数据/旧 checkpoint 的 self-play 数据（experience replay / 数据配比调度）。
- 类 league 的做法：**Policy Pool**——保留历史策略 checkpoint，用"当前策略 vs 旧 checkpoint"当对手对局，避免策略漂移到只擅长新场景而丢掉旧博弈技能（与第 5 节方向 3 同源）。

**第三层：多级评估门禁（改动上真车前的"安全闸"）。**
```
冒烟(单场景调试) → 回归库(全量场景) → 分布/鲁棒性统计(随机种子×场景批量)
  → 拟真度评估(WOSAC/human-replay) → 影子模式/仿真车队 → 受控路测
```
- 每一级都能用三份工作的资产实现：PufferDrive 提供 1-3 级的廉价闭环，WOSAC 提供 4 级，human-replay/mixed-play 提供"与人类兼容性"的中间检查点，GigaPixel 的感知适配管线提供"仿真策略→真实数据"的接驳方法。
- **门禁必须可回滚**：每次改动保留旧 checkpoint 与新 checkpoint 的对拍结果表，任何一项门禁掉点 → 自动触发对拍报告，而不是静默通过。

### 6.5 把自博弈直接变成"调试机器"：仿真驱动的故障发现闭环

这是三份工作综合起来最有价值的工程范式：

```
自博弈大规模滚动(PufferDrive/GigaFlow 风格)
   │  自动记录：碰撞/近失(miss-distance)/逼停/死锁/出路 事件
   ▼
失败场景自动挖掘 → 去重/聚类 → 注入 场景库
   │                                    │
   │  （成为第 6.4 层的回归集，持续增长）  │
   ▼                                    ▼
定向修复(数据/奖励/架构) ────────→ 回归门禁 + Policy Pool 防遗忘
   │
   ▼
新策略再进入自博弈 → 旧问题被"教不会"的假说自动被门禁拦下
```

- **为什么自博弈最适合当调试机器**：对手是活的——当策略修好某 bug 后，自博弈会自动生成更难/更接近边界的同类场景，逼着归因与修复往深走；而固定日志回放永远生成不了"新修好后的新失败"。
- **PufferDrive 是这种循环的最廉价载体**：15 分钟能从零训到 80%，意味着"改一行奖励 → 看对旧场景的影响"的实验周期在小时级——这是黑盒系统唯一可靠的迭代方式：**把试错成本压到足够低，让归因假设能被快速证伪**。

### 6.6 给"两端式"与"一段式"团队的分头建议

**两端式（有中间语义接口）**
- 重点建设**中间产物监控与断言**：检测/预测/占用头各自独立跑 PufferDrive 指标（检测 AP、预测 minADE、planner 冲突率），形成"哪一段先劣化"的早期报警。
- 用**接口冻结对照**修 bug：怀疑下游就冻结上游权重只训 planner；怀疑上游就用 oracle 中间产物喂下游。
- 警惕**累积误差**：两段各 95% 正确，级联后可能只有 70%；归因时务必做"真值接口注入"看每级放大系数。

**一段式（纯黑盒）**
- 尽早把架构做成 **teacher/student 双通道**（即便训练时不强制蒸馏），保留"接 oracle 输入跑闭环"的调试模式——这是你唯一能拆开"感知 vs 决策"的扳手（GigaPixel 已验证该架构可训练且可落地）。
- 用**行为签名 + 反事实编辑**代替内部归因；建立"输入扰动响应曲线"（如对横向偏移、对遮挡的灵敏度）作为策略的"可解释体检表"。
- 每个版本发布时同步发布"privileged 对照分数 vs sensor 分数"，两者之比就是**黑盒透明度指标**——比值异常变大 = 感知在退化，先别急着怪 planner。

## 7. 对本项目（PufferDrive）的落地建议小结

PufferDrive 目前是最适合作为"归因实验室 + 回归门禁"的平台：

1. **补一个"oracle 注入调试模式"**：目前有 `control_sdc_only`/mixed-play/human-replay，但缺少"让自车策略吃真值状态（privileged）"的对照开关——加上它，本仓库就自带两端式归因所需的 A/B 对照。
2. **把 benchmark/ 里的评估器升级为"回归门禁 CLI"**：输入 = 场景库目录 + 新旧 checkpoint，输出 = 逐场景对拍表 + 门禁通过/失败，可挂 CI。
3. **推广 mixed-play 的"对手采样分布"为训练期配置**，让自博弈默认带一定比例的人类日志回放与历史 checkpoint，抑制单均衡/遗忘问题。
4. **Roadmap 对齐**：agent diversity（异质车流）、traffic light、2.5D 立交等已列 3.0 规划，正是扩大归因场景覆盖面的方向。
